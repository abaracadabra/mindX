# The Inverse Debt Layer: Profit from Loss via Bitcoin Anchoring

This document covers the four contracts that extend the base DELTAVERSE protocol into a system that explicitly produces profit from nominal loss by anchoring the accounting to Bitcoin as the hard-money numeraire. If you have already read `ARCHITECTURE.md` and `thesis.md`, this is where you learn how the profit-from-loss mechanic actually works at the contract level.

## The problem this layer solves

The base protocol already lets traders profit from rising debt stress by opening leveraged shorts on the Global Debt Stress Index. But it measures that profit in USDC, which is a dollar-denominated claim on the same debt system the protocol is shorting. A trader who earns twenty percent in USDC during a fifteen percent dollar debasement has really only earned five percent in hard-money terms. This accounting understatement is not a small correction — in an acute debasement scenario like 1971 or 1985 it can be the entire story. The inverse debt layer fixes this by making Bitcoin the explicit numeraire against which real purchasing power is measured.

The architecture does not replace the base stack. The existing `DebtInheritanceProtocol` keeps issuing sGDSI, the existing `PerpetualEngine` keeps opening leveraged positions, and the existing `CrossCollateralVault` keeps accepting tokenized debt as collateral. What changes is that a user who holds an sGDSI position or has just closed a thesis can now route their USDC proceeds into a new synthetic token, `iDEBT`, whose redemption value tracks a composite of the debt stress index and the Bitcoin price together. When either component rises, the token pays more. When both rise together — the thesis's central prediction — it pays the most.

## The four contracts and how they compose

`BitcoinAnchorOracle.sol` is the bottom of the new stack. It aggregates BTC/USD price from Chainlink and Pyth with configurable weights, applies EMA smoothing to reject short-term manipulation, and exposes a `latestPrice()` view that returns the eighteen-decimal BTC/USD rate. It deliberately avoids using reporter medians because BTC/USD is one of the most liquid price pairs on earth — Chainlink and Pyth together give more than enough coverage, and adding a third source would only add attack surface. A twenty-percent deviation cap per update prevents a single bad data point from moving the oracle more than markets actually move in a single update cycle.

`DebasementIndex.sol` sits above the BitcoinAnchorOracle and combines it with the existing `DeltaVerseDebtOracle`. On initialization, it locks in a baseline snapshot of both the GDSI value and the BTC/USD price at deployment. From that point forward, the `currentIndex()` function returns a weighted average of the ratios — how much GDSI has moved against its baseline, and how much BTC has moved against its baseline. The default weighting is forty percent GDSI, sixty percent BTC, giving more weight to the market aggregate while still letting the protocol's internal debt stress measurement contribute. If GDSI doubles and BTC doubles, the debasement index rises to 2.0. If both stay flat, it stays at 1.0. If one rises and the other falls, they partially cancel.

`InverseDebtToken.sol` is the user-facing contract where the profit-from-loss mechanic lives. Users mint iDEBT by depositing USDC at the current debasement index: the formula is `iDEBT_out = (usdc_in × BASE) / current_index`. When the index is 1.0 (baseline), one hundred USDC mints roughly one hundred iDEBT less fees. When the index has risen to 1.5 (significant debasement has occurred since deployment), one hundred USDC mints only sixty-seven iDEBT — which is correct, because the dollar has lost purchasing power and each iDEBT now represents a larger claim. Later, when the user burns iDEBT, the formula inverts: `usdc_out = (iDEBT_in × current_index) / BASE`. If the index rose between mint and burn, the user receives more USDC than they deposited. This is the profit-from-loss mechanic encoded as a single equation.

`BitcoinProfitRecognizer.sol` is a stateless composition helper that chains together the existing protocol's sGDSI burn and the new iDEBT mint into a single atomic transaction. Without the recognizer, a user holding sGDSI who wants to convert into iDEBT would have to perform two transactions, paying gas twice and exposing themselves to oracle movement in the window between the burn and the mint. The recognizer performs both atomically and emits a single `RecognizedProfit` event carrying the full trail — the sGDSI burned, the USDC proceeds, the iDEBT minted, and the current BTC satoshi equivalent. The subgraph indexes this as one semantic action rather than two unrelated events.

## The math, written out plainly

At time `t_0` the user mints. The debasement index is `I(t_0) = w_gdsi · (gdsi(t_0) / gdsi_base) + w_btc · (btc(t_0) / btc_base)`. Since `gdsi(t_0) = gdsi_base` and `btc(t_0) = btc_base` at baseline, this equals one exactly. As time passes and the oracles update, the ratios can diverge from one in either direction. At burn time `t_1` the user holds `q` iDEBT tokens minted at index `I(t_0)`. They receive USDC equal to `q · I(t_1) / I(t_0)` ignoring fees. If `I(t_1) > I(t_0)`, the payout exceeds the deposit — profit measured in USDC terms. The BTC-equivalent of that payout is `payout · 10^18 / btc(t_1)`, expressed in satoshis. Because BTC is part of the debasement index, a rise in BTC itself partially lifts the index, meaning the USDC payout grows as BTC grows — but since we are also paying in USDC rather than BTC, the user's real BTC-denominated profit depends on whether the index rose by more or less than BTC itself. This is the key subtlety: the design does not promise constant BTC value, it promises payouts that move in the direction of the debasement thesis and that can be measured honestly against BTC for real-profit accounting.

## The haircut under extreme debasement

In a scenario where the debasement index rises faster than the contract's stablecoin reserves can accommodate, the `burn` function pays out whatever USDC is available rather than reverting. This is deliberate. A protocol that reverts under stress is pretending the stress does not exist. A protocol that pays out proportionally under stress is honest about the scenario while keeping the user whole in direction: they still receive their share of the available pool, they still realize the BTC-denominated upside through other legs of the system (their iDEBT tokens are still outstanding and backed by the reserve, the sGDSI position they may still hold, or their direct exposure to the thesis). Reverting is the failure mode of protocols that have not thought carefully about their own terminal state. Paying out what exists is the failure mode of protocols that have.

## How a user experiences the system end to end

Alice deposits ten thousand USDC into the base protocol's `mintSGdsi()` at a GDSI of one thousand and a BTC price of sixty thousand. She holds her sGDSI for six months. During that period, global debt stress rises from one thousand to twelve hundred (twenty percent increase) and BTC rises from sixty thousand to ninety thousand (fifty percent increase). The debasement index, using the default 40/60 weighting, rises to `0.4 × 1.2 + 0.6 × 1.5 = 0.48 + 0.90 = 1.38`. Alice calls the `BitcoinProfitRecognizer.recognizeProfit()` function with her sGDSI tokens. The recognizer burns her sGDSI in the base protocol and receives USDC; the USDC amount depends on how the GDSI alone moved (twenty percent upward, so roughly twelve thousand USDC before fees). The recognizer then mints iDEBT from the InverseDebtToken contract with that USDC, at the current debasement index of 1.38, giving Alice iDEBT tokens representing her now-appreciated position. She sees the `RecognizedProfit` event showing her USDC proceeds of twelve thousand and a BTC satoshi equivalent of roughly 13.3 million satoshis (0.133 BTC). Six months later, debasement continues; the index has risen further to 1.6. Alice burns her iDEBT and receives more USDC than she put in — not just once, but on top of the gains she already captured when she converted from sGDSI. She has profited twice: once from the GDSI rise during the first leg, and again from the combined debasement during the second leg, with every transition measured honestly in Bitcoin-equivalent terms.

## Integration with governance and pause infrastructure

All four new contracts are `AccessControl` + `Pausable`. Their `DEFAULT_ADMIN_ROLE` is held by the deployer at deploy time and must be transferred to the `DeltaVerseTimelock` as part of the post-deployment checklist. Once transferred, parameter changes (fee rates, source weights, oracle staleness thresholds) can only happen through governance proposals with the standard forty-eight-hour delay. The `EmergencyPauser.managedContracts` array should be extended to include all four new contracts so that guardians can pause the inverse-debt layer independently of the base stack if a specific issue is found. The inverse-debt layer's pause does not interrupt the base protocol — users can still interact with the existing sGDSI system, they just cannot mint or burn iDEBT during the pause window.

## What still needs building

The inverse-debt layer is self-contained but the broader protocol still has pending work. The keeper bot that updates the `BitcoinAnchorOracle.updateComposite()` is not yet written but is a straightforward extension of the existing sub-index finalizer pattern. The subgraph schema needs entries for `InverseDebtMint`, `InverseDebtBurn`, and `RecognizedProfit` events. The frontend at `agenticplace.pythai.net` needs UI flows for the new mint/burn/recognize paths. None of these are blockers for deployment — the contracts are live-ready as soon as the existing keeper infrastructure is extended to call `btcOracle.updateComposite()` on the same cadence as the Pyth updater.
