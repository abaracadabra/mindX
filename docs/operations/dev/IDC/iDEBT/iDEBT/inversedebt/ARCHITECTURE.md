# DELTAVERSE Debt Inheritance Protocol — Architecture Map

This document is your orientation guide to the repository. If you are reading the code for the first time, start here. The purpose is not to re-explain what each contract does (the README and the NatSpec comments do that) but to give you a mental model of how the pieces fit together so you can navigate directly to whatever you came for without spending hours reverse-engineering the directory structure.

## The Seven Layers

The repository is organized into seven layers, stacked conceptually from deepest (closest to the economic logic) to shallowest (closest to the user or operator). Each layer depends on the ones below it and provides abstractions to the ones above it.

Layer one is the economic primitives. These live in `src/` and consist of five Solidity contracts that implement the core building blocks of the protocol. `RWAToken.sol` represents a tokenized off-chain debt instrument with compliance gating. `CrossCollateralVault.sol` accepts multiple asset types as collateral and issues stablecoin loans. `PerpetualEngine.sol` runs leveraged directional positions with funding rates and insurance. `DeltaVerseDebtOracle.sol` produces a composite Global Debt Stress Index from multiple data sources using Synthetix V3 oracle manager patterns. `DebtInheritanceProtocol.sol` is the capstone orchestrator that composes the other four into the recursive thesis expression flow. Read this layer first if you want to understand what the protocol does economically.

Layer two is the governance trust boundary. These contracts live in `src/governance/` and they are what makes the protocol credibly neutral after deployment. `DeltaVerseTimelock.sol` is a thin wrapper around OpenZeppelin's `TimelockController` that enforces a mandatory delay between when a parameter change is proposed and when it can be executed. `DeltaVerseGovernor.sol` is the token-weighted voting contract that decides which proposals get queued in the timelock. `EmergencyPauser.sol` is the fast-path circuit breaker controlled by a multisig of guardians whose only power is stopping the protocol. Read this layer when you want to understand who holds power over the protocol and on what timeline they can exercise it.

Layer three is the deployment and testing infrastructure. The `script/Deploy.s.sol` Forge script deploys all five operational contracts in the correct dependency order and prints a post-deployment checklist of the wiring steps that must be performed through governance proposals. The `test/DebtInheritanceProtocol.t.sol` file provides integration tests with inline mocks for stablecoin, Chainlink feeds, and Pyth, verifying that the full recursive thesis flow works end-to-end. The `foundry.toml` file configures the Solidity compiler, the test fuzzer, and the RPC endpoints for multi-chain deployment. Read this layer when you want to actually run the code or deploy it.

Layer four is the keeper automation. The `keepers/` directory contains a TypeScript project built with viem that runs four off-chain bots. `pythUpdater.ts` fetches signed price updates from the Pyth Hermes API and pushes them to the on-chain Pyth contract. `subIndexFinalizer.ts` finalizes each sub-index from reporter data and calls `updateComposite()` to refresh the GDSI. `feeRouter.ts` watches `pendingFees` on the protocol and calls `routeFees()` when the accumulated amount exceeds a gas-profitable threshold. `liquidator.ts` scans the vault and perp engine for undercollateralized positions and calls `liquidate()` to capture bonuses. The `Dockerfile` provides a multi-stage production container with a non-root user. Read this layer when you want to understand what has to run off-chain for the protocol to function.

Layer five is the observability infrastructure. The `subgraph/` directory contains a Graph Protocol subgraph that indexes the protocol's on-chain events into a queryable GraphQL API. The `schema.graphql` file defines the entity types (Protocol, User, SgdsiMint, SgdsiBurn, ThesisPosition, OracleSnapshot, LpStaker, HourlyStat). The `subgraph.yaml` manifest wires contracts to event handlers. The `src/mappings/protocol.ts` and `src/mappings/oracle.ts` files are the AssemblyScript handlers that translate events into entity updates. Read this layer when you want to build a dashboard, an analytics query, or any off-chain system that needs to know what the protocol has done historically.

Layer six is the audit preparation. The `audit/` directory contains four documents and configuration files that prepare the codebase for third-party security review. `SCOPE.md` declares the contract inventory, trust model, invariants, and attack surface summary. `KNOWN_ISSUES.md` discloses design compromises the team has already accepted. `slither.config.json` configures the Slither static analysis tool to match the project's compilation settings. `.mythril.yml` configures the Mythril symbolic execution tool for deeper bytecode analysis. Read this layer when you want to understand what the team thinks the risks are or when you are the auditor.

Layer seven is the infrastructure orchestration. At the root of the repository, `docker-compose.yml` coordinates the four keeper containers, a Prometheus metrics collector, and a Grafana visualization stack. `.env.example` is the template for the environment variables that the keepers need, organized by category with extensive comments. `monitoring/prometheus.yml` configures Prometheus to scrape the keepers (pending the addition of a metrics endpoint in a future keeper enhancement). The top-level `README.md` and this `ARCHITECTURE.md` file provide the entry points for a reader. Read this layer when you want to actually run the whole stack on a real server.

## How the Layers Interact

Understanding the static layout is one half of the mental model; understanding the dynamic interactions is the other half. Let me walk through three representative flows to show you how the layers cooperate at runtime.

The first flow is a user minting sGDSI. The user sends an Ethereum transaction to `DebtInheritanceProtocol.mintSGdsi()`, which is layer one. The contract reads the current composite value from `DeltaVerseDebtOracle`, which is also layer one. The oracle has that composite value because the layer four keeper (`subIndexFinalizer.ts`) recently called `finalizeSubIndex()` and `updateComposite()`, which themselves depended on the layer four keeper (`pythUpdater.ts`) having recently pushed fresh Pyth data. The mint succeeds, and emits `SGdsiMinted` event. The event is picked up by the layer five subgraph's `handleSgdsiMinted` handler, which updates the `Protocol` and `User` entities and creates an immutable `SgdsiMint` record. A frontend watching the subgraph sees the mint and displays it in the user's position history. Six layers cooperated for one user action; that is production DeFi.

The second flow is a governance parameter change. A token holder with enough stake calls `propose()` on the layer two Governor, describing a change to the oracle's heartbeat threshold. Voters cast votes during the one-week voting window. If quorum and a majority are reached, the proposal enters the Succeeded state. Anyone calls `queue()` which schedules the underlying calls in the layer two Timelock. After forty-eight hours of mandatory delay, anyone calls `execute()` which causes the Timelock to actually invoke the oracle's `setHeartbeat()` function. The oracle verifies the caller is the Timelock (via `DEFAULT_ADMIN_ROLE`) and applies the change. Layers one and two cooperated, and a layer three keeper running `subIndexFinalizer.ts` will start using the new heartbeat on its next cycle without any code change.

The third flow is an emergency response. A guardian notices anomalous oracle behavior in real-time monitoring. They connect their hardware wallet to the layer two `EmergencyPauser` and call `pauseAll()`, which uses low-level calls to invoke `pause()` on every managed contract in a single transaction. Layer one state is now frozen. The guardian files an incident report. The team investigates and determines the cause. If the cause requires a parameter change, they follow the governance flow described above (but with a shortened voting period via emergency proposal). If it requires a new contract deployment, they use the layer three Forge script to deploy the fix, then follow governance to migrate. If the issue is resolved and the protocol can safely resume, the Timelock calls `unpauseAll()` on the EmergencyPauser after the cooldown elapses. Layers one, two, and three all participated in the incident response.

## Where to Start Reading

If you are new to the repository, read the files in this order.

Start with the three thesis papers in `docs/`. The first paper (`global_debt_thesis.docx`) explains why the protocol exists at all. The second paper (`cryptographic_inheritance.docx`) describes the mechanism for translating the thesis into on-chain contracts. The third paper (`recursive_proof_part3.docx`) contains the capstone proof that the mechanism is executable. Together they take about thirty minutes to read and give you the economic and philosophical context you need to understand why the code does what it does.

Next, read `src/DebtInheritanceProtocol.sol`. This is the capstone contract, and reading it first gives you the thesis-to-code mapping most directly. Focus on `mintSGdsi`, `burnSGdsi`, `expressThesis`, and `closeThesis`. The other functions are auxiliary. Do not yet try to understand the contracts it calls; just note that it depends on a vault, an oracle, a perp engine, and a stablecoin, and trust that each does what its name suggests.

Next, read the four contracts that the capstone depends on, in this order: `DeltaVerseDebtOracle.sol`, `CrossCollateralVault.sol`, `PerpetualEngine.sol`, `RWAToken.sol`. The order matters because each depends conceptually on the ones before it. After this step you will understand the full economic layer.

Next, read the governance layer in this order: `DeltaVerseTimelock.sol`, `DeltaVerseGovernor.sol`, `EmergencyPauser.sol`. This is fast because the Timelock and Governor are thin wrappers around OpenZeppelin and the EmergencyPauser is small.

Next, read the integration test file `test/DebtInheritanceProtocol.t.sol`. This will show you the protocol in motion: how the contracts are deployed, how they are wired, and how a full thesis round-trip plays out on-chain. This is often the fastest way to understand a DeFi protocol because tests show you the intended use cases stripped of all adversarial framing.

Next, read the keeper code in this order: `keepers/src/config.ts` first for the environment setup, then `keepers/src/pythUpdater.ts`, `keepers/src/subIndexFinalizer.ts`, `keepers/src/feeRouter.ts`, `keepers/src/liquidator.ts`, and finally `keepers/src/index.ts` for the orchestration. This tour gives you the complete picture of what has to run off-chain.

Finally, read `subgraph/schema.graphql` and one of the two mapping files. This shows you what the protocol looks like through an analytics lens and gives you the vocabulary for building any dashboard or data query you might need.

After all of this, the audit materials in `audit/` should feel like a natural conclusion: they summarize everything you have just read from the perspective of somebody trying to find what could go wrong. Read `SCOPE.md` first, then `KNOWN_ISSUES.md`, and you will have a complete mental model of the protocol, its risks, and its defenses.

## The Deployment Sequence

The final piece of the architectural picture is the deployment sequence. A working mental model of the repository is incomplete without knowing how a fresh deployment actually goes from nothing to a live protocol. This is the condensed version; the detailed checklist is in `script/Deploy.s.sol` and in the post-deployment checklist it prints.

Phase one is contract deployment. The deployer runs the Forge deployment script, which deploys the five operational contracts in the correct dependency order, deploys the three governance contracts, and prints the addresses. At this point the contracts exist but the protocol cannot yet operate because no collateral is registered, no oracle sources are configured, no insurance fund is seeded, and the deployer still holds admin rights.

Phase two is configuration. The deployer calls `addAsset()` on the vault to register each collateral type with its Chainlink feed and parameters. The deployer calls `setChainlinkSource()` and `setPythSource()` on the oracle to wire each sub-index to its data sources. The deployer seeds the insurance fund on the perpetual engine. The deployer seeds the vault with stablecoin reserves so that borrows can actually pay out.

Phase three is bootstrapping the oracle. Reporters submit initial sub-index values, the keeper finalizes each sub-index, the composite is computed, and the oracle enters the healthy state. The first `updateComposite()` call establishes the baseline GDSI value from which all subsequent movements are measured.

Phase four is the governance handover. The deployer transfers `DEFAULT_ADMIN_ROLE` on every operational contract to the `DeltaVerseTimelock`. The deployer grants `PROPOSER_ROLE` on the Timelock to the `DeltaVerseGovernor` and revokes the deployer's own proposer rights. The deployer renounces `TIMELOCK_ADMIN_ROLE`. At this point the protocol is self-governing and the deployer has no remaining privileged access.

Phase five is keeper activation. The operations team starts the Docker Compose stack, configures the environment variables, and verifies through Prometheus that each keeper is running. The Pyth updater begins its minute-by-minute rhythm, the sub-index finalizer begins its four-hour cycle, the fee router begins its hourly check, and the liquidator begins its thirty-second scan.

Phase six is frontend and subgraph deployment. The subgraph is deployed to The Graph's hosted service or a self-hosted indexer, configured to watch the deployed contract addresses. The frontend at `agenticplace.pythai.net` is pointed at the subgraph and the contract addresses, and users can begin interacting with the protocol through the UI.

After phase six, the protocol is live. Users can mint sGDSI, express theses, and the oracle's LP stakers begin earning routed fees. Governance proposals can be submitted to tune parameters. Guardians stand ready to pause in an emergency. The thesis that began in `global_debt_thesis.docx` is now running on mainnet, and the debt inheritance can begin.
