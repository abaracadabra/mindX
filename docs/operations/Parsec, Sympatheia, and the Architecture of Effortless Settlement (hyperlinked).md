### AgenticPlace — the marketplace layer

The [AgenticPlace homepage](https://agenticplace.pythai.net/) describes itself, verbatim, as a service that *"indexes the global ERC-8004 registry across 48 chains and extends it with Algorand-native minting, verification, and oracle attestation."* This is the marketplace where agents become discoverable, where their reputation accrues, where their work is minted into a form that can be transferred, attested, and economically priced. The page exposes four mint types — `aNFT` (immutable), `dNFT` (dynamic), `iNFT` (intelligent), and `THOT` (a knowledge-tensor primitive) — and it accepts `Pera / Parsec` as signers, which is the first public confirmation that the parsec-wallet org is part of the same signing surface as the canonical Algorand wallet. The meta-keywords on the homepage explicitly enumerate *"PYTHAI, mindX, Parsec Wallet, x402, OASF"* together, which is the operative cross-link between the wallet, the protocol, and the marketplace. The integration is documented from the mindX side at [`/doc/AgenticPlace_Deep_Dive`](https://mindx.pythai.net/doc/AgenticPlace_Deep_Dive) (an 80.5 KB internal reference), and the mindX API exposes three direct AgenticPlace routes: `POST /agenticplace/agent/call`, `GET /agenticplace/ceo/status`, and `POST /agenticplace/ollama/ingest` (all enumerated in the [mindX API ReDoc](https://mindx.pythai.net/redoc)).

The marketplace's minting pipeline is governed by ARC-19 and ARC-69 on Algorand. ARC-19 — formally specified in the Algorand Foundation's `arc-0019` document — uses a `template-ipfs://{ipfscid:<version>:<multicodec>:reserve:<hash>}` URL whose 32-byte reserve address can be rewritten by an `acfg` transaction, which is how a `dNFT` or an `iNFT` *mutates without losing identity*. ARC-69 supplies on-chain JSON metadata for the static `aNFT` case and the more traditional NFD entries. NFDomains V3 is the naming layer: NFDomains' own [FAQ](https://docs.nf.domains/nfd-docs/fundamentals/faq) states verbatim that *"NFDs are smart contracts that mint their own ARC-19 NFT that acts as a dynamic representation of the NFD in your wallet."* The result is that a phrase like `codephreak.algo` is simultaneously a wallet address, a brand, and an avatar, with forward and reverse lookups against a global registry contract. The `agenticplace-chain` monorepo is the codebase that ties these primitives together — ARC-19/ARC-69 NFD minting, the NFDomains V3 integration, the parsec-wallet TypeScript shim, and the `allchain` CAIP-2 loader. (The shim and the loader are described below in section VI.)

## III. The Inaugural Announcement of `github.com/parsec-wallet`

Parsec is the wallet that the BANKON ecosystem has been quietly building. The [GitHub organization](https://github.com/parsec-wallet) is public, currently lists fifty-three repositories, identifies its homepage as [`bankon.pythai.net`](https://bankon.pythai.net/), and signs its public README as *"a wallet systems laboratory: a deliberately broad collection of repositories spanning wallet frontends, chain infrastructure, signing stacks, hardware wallet integrations, distributed-web tooling, token-onboarding utilities, standards references, and experimental protocol work."* The same README declares the canonical implementation target as *"Tauri + Rust backend + zero-dependency TSX/CSS frontend + Tomb-backed local vault."* Tauri gives the wallet a small attack surface and a single binary across Linux, macOS, and Windows; Rust gives it the memory-safety guarantees that any signing stack must have; the zero-dependency TSX/CSS frontend means that the renderer cannot be silently subverted by an npm supply-chain attack; and `Tomb` — the dyne.org fork archived in the [Professor-Codephreak](https://github.com/Professor-Codephreak) repositories — provides the LUKS-encrypted local vault that holds seeds at rest. The pinned `slingshot` repository sits in the org as the long-range protocol-design seed, with the canonical TypeScript signing components (`signatory`, `safe-wallet-web`, `xchainjs-lib-1`, `parsec-pod`) and the Bitcoin-L1 `opnet` / `walletconnect` forks filling out the chain-coverage surface.

### Parsec as a branded abstraction over GoPlausible x402-avm

The most important thing to say about parsec-wallet, and the thing that justifies treating this essay as a *first public statement of intention*, is that parsec-wallet does not reinvent the x402 stack. The actual Algorand implementation of x402 is [GoPlausible's x402-avm](https://x402.goplausible.xyz/), the reference suite documented by the Algorand Foundation as the canonical AVM track of the protocol. Its packages — `@x402-avm/core`, `@x402-avm/avm`, `@x402-avm/express`, `@x402-avm/next`, `@x402-avm/hono`, `@x402-avm/axios`, `@x402-avm/paywall`, and `@x402-avm/extensions` — implement the `exact` payment scheme via 2-transaction atomic groups with pooled fees, the V2 CAIP-2 network identifiers (`ALGORAND_MAINNET_CAIP2 = "algorand:wGHE2Pwdvd7S12BL5FaOP20EGYesN73ktiC1qzkkit8="` and `ALGORAND_TESTNET_CAIP2 = "algorand:SGO1GKSzyE7IEPItTxCByw9x8FmnrCDexi9/cOUJOiI="`), and the Bazaar discovery extension that allows facilitators to catalog paid resources automatically.

Parsec wraps that stack and extends it. It adds **Algorand State Proofs (ASPs)** — Falcon-512-based post-quantum attestations of historical chain state, deployed on the Algorand mainnet since September 2022 — exposed as a first-class wallet capability so that any signing flow can be conditioned on a state-proof witness. It adds ARC-52 HD wallet support — the Algorand Foundation's implementation of BIP32-Ed25519, whose underlying key-derivation scheme was specified by Khovratovich and Law in *"BIP32-Ed25519: Hierarchical Deterministic Keys over a Non-linear Keyspace"* (IEEE EuroS&P 2017) — letting a single Parsec seed deterministically derive an Algorand address (`m'/44'/283'/0'/0/0`), an identity key, and a per-app change index that supports the DAO-voting and ring-signature workflows ARC-52 was designed for. And it adapts the Pera multisig flow so that a Parsec wallet can sign as a member of an existing Pera msig vault, which is the bridge that lets the parsec-wallet stack inherit the existing institutional muscle of the Algorand ecosystem rather than fight it.

## IV. DAIO Pre-Deployment Technical Summary (Architecture B)

The DAIO — Decentralized Autonomous Intelligent Organization — is the constitutional layer that BANKON is preparing to deploy. The canonical mindX-side reference is the [DAIO Framework doc](https://mindx.pythai.net/doc/DAIO), which states the technical stack directly: *"On-chain governance with Solidity smart contracts, Foundry toolchain, OpenZeppelin contracts. The third pillar of the Manifesto."* The civilizational framing — what the DAIO is *for* — is set out in the longer [DAIO Civilization Governance doc](https://mindx.pythai.net/doc/DAIO_CIVILIZATION_GOVERNANCE), which describes the 2/3 consensus model across Marketing, Community, and Development as *"governance as civilization-building."*

Architecturally the DAIO is a dual-chain system: an *Algorand constitutional layer* (where Algopy contracts encode the slow, agent-bearing, consensus-heavy rules — the Roman-republic logic of the BONAFIDE suite, the registry of agent identities, the Sun Tzu doctrine validators of the SOUL layer) and an *EVM economic layer* (where the DELTAVERSE Solidity contracts encode the fast, capital-bearing, MEV-aware machinery of debt, debasement, and liquidity). The DELTAVERSE-side architecture is documented at [`/doc/DeltaVerse`](https://mindx.pythai.net/doc/DeltaVerse) (a 35.2 KB internal reference). The two chains are bridged by **openBDK**.

### openBDK as the bridge fabric

`openBDK` is the canonical Polygon Chain Development Kit pattern, with three contract roles ported from the well-documented Polygon Staking-the-Bridge architecture: an `L1Escrow` that locks the underlying ERC-20 on Ethereum and emits a unified-bridge message; an `L2MinterBurner` that receives that message and natively mints the L2 representation through an `L2Token` contract; and a `NativeConverter` that supports 1:1 conversion between the natively-minted STB tokens and the bridge-wrapped LxLy variant. On top of those three roles, openBDK adds a `1 Relayer + 3 Validator` BFT topology — a minimal honest-majority quorum that lets the bridge cross-attest messages without relying on a single sequencer. The canonical Unified Bridge address on Ethereum mainnet is `0x2a3DD3EB832aF982ec71669E178424b10Dca2EDe`, which is the contract that openBDK composes with rather than replaces.

### pontifex — the xERC20 sovereignty layer

Where openBDK is the bridge fabric, `pontifex` is the sovereignty layer that sits on top of it. It is an xERC20 implementation in the Latin tradition the BANKON stack favors — every component named for the Roman office it inherits — with a *golden-ratio Troll toll* mechanism whose fee schedule is parameterized by `AURUM_E18 = φ × 10¹⁸`, the integer fixed-point encoding of φ (the golden ratio) scaled to eighteen decimals. The Troll toll is the levy charged by the bridge for the right to mint or burn xERC20 supply on a chain; pricing it at φ rather than at a flat percentage is not a marketing flourish but a deliberate choice to keep the toll on a logarithmic schedule that converges toward neutrality as volume grows.

### SPINTRADE — the DEX

`SPINTRADE` is the canonical DEX leg of the architecture. It is a Uniswap v2 fork on Moonbeam, extended with NFT-positioned liquidity (so that LP shares are themselves transferable, mintable assets) and XCM routing (so that swaps can natively route across Polkadot parachains). Pinned in the [Professor-Codephreak inventory](https://github.com/Professor-Codephreak) alongside `smartmetamask`, it is the venue where BANKON tokens, DELTAVERSE debt positions, and pontifex-wrapped xERC20s find their two-sided markets.

### iDEBT — sovereign debt positions

`iDEBT` is the protocol that turns a debt obligation into an ERC-721. Each iDEBT NFT is a sovereign debt position with a Merkle-committed *heir set* — a binding commitment to the addresses or keys that may inherit the obligation if the principal becomes uncontactable — and a DAIO governance hook that lets the iDEBT contract accept policy changes only when ratified by the [Boardroom](https://mindx.pythai.net/doc/daio/governance/boardroom.py). This is the layer where Buddhist *śūnyatā* enters the system: a debt position has no intrinsic essence; it exists only as the dependent arising of a creditor, a debtor, an heir set, and a governance body. Without those four, the NFT is empty in the precise Madhyamaka sense — and that emptiness is what makes it transferable, partitionable, and forgivable without losing identity.

### DELTAVERSE — Debt Inheritance Protocol (12 EVM contracts, parallel Algorand port)

The [DELTAVERSE suite](https://mindx.pythai.net/doc/DeltaVerse) is twelve EVM contracts that together implement the Debt Inheritance Protocol: among them, `BitcoinAnchorOracle` (which reads the Bitcoin chain-tip via SPV proofs and anchors EVM state to Bitcoin block hashes), `DebasementIndexV2` (which tracks the M2-equivalent debasement of fiat against a basket of stablecoins), `InverseDebtToken` (a synthetic that pays positive yield when sovereign debt is being repaid and negative yield when it is being inflated), `GlobalCurrencyBasket` (the SDR-equivalent multi-currency aggregator), and `SovereignDebtRegistry` (the registry of issued iDEBT positions indexed by jurisdiction). The remaining seven contracts complete the loop: oracles, governance hooks, fee distributors, and the cross-chain message receivers that pair with Wormhole and openBDK. A parallel Algorand/Algopy port mirrors all twelve in TEAL-compiled Python, so that DAIO can settle the same logic on the constitutional layer when latency or finality demands.

The on-chain anchor of mindX-side intelligence is the `NeuralNode` contract, deployed on Polygon at `0x024b464ec595F20040002237680026bf006e8F90`, which serves as the on-chain attestation point where mindX-trained models commit their fingerprints. The ERC-8004 identity and reputation registries live at CREATE2-anchored canonical addresses on every EVM chain: `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` for Identity and `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` for Reputation. ## V. x402 — the Payment Protocol

x402 is the protocol that converts HTTP's `402 Payment Required` status — first defined in RFC 2068 (1997) and held *"reserved for future use"* through RFC 7231 (June 2014) — into a working payment rail for agentic commerce. The x402 specification, published by Coinbase Developer Platform on May 6, 2025, defines a three-party flow: a client requests a resource; the server replies with `402` plus a `PAYMENT-REQUIRED` envelope describing accepted schemes, networks, prices, and recipients; the client signs a `PaymentPayload` and retries with a `PAYMENT-SIGNATURE` header; the server validates the payload (locally or via a facilitator) and serves the resource. On EVM rails the dominant settlement path is EIP-3009's `transferWithAuthorization` over USDC, with Permit2 as the universal fallback for any other ERC-20; on Algorand the equivalent path is the [GoPlausible `exact` AVM scheme](https://x402.goplausible.xyz/), which constructs a 2-transaction atomic group and uses pooled fees to abstract gas away from the client. CAIP-2 is the standard format for identifying chains across the V2 spec — `eip155:8453` for Base mainnet, `algorand:wGHE2Pwdvd7S12BL5FaOP20EGYesN73ktiC1qzkkit8=` for Algorand mainnet — and ERC-8004 supplies the identity and reputation registries that x402 facilitators consult for trust scoring.

This is *wu wei* in protocol form. Lao Tzu's instruction is to act without forcing, to let the structure of the world carry the action; x402 lets the structure of HTTP carry the payment. There is no payment page, no redirect, no webhook reconciliation loop — the payment is part of the request, settled in the same round-trip. mindX uses this directly: every paid inference endpoint is gated by an `@x402-avm/express` (or `@x402-avm/next`) middleware, with `payTo` set to a BANKON-managed Algorand address and `price` set in USDC ASA terms (`31566704` on mainnet). BANKON identity binds the recipient: the `payTo` address is resolvable to an ERC-8004 reputation record via the [Dojo](https://mindx.pythai.net/doc/daio/governance/dojo.py) and the [Identity Sync Tool](https://mindx.pythai.net/doc/identity_sync_tool), so an agent paying a service can audit who it is paying *before* it signs.
