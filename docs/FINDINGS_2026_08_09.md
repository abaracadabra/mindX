# Findings — 2026-08-09/10

An outage investigation that turned into a memory-retention design, a training
audit, and a public observation surface. Written down because several of these
are traps that already bit this codebase once before, and one of them would have
destroyed memory if it had been "fixed" the obvious way.

---

## 1. The outage: one event loop, two jobs

`mindx.pythai.net` stopped accepting connections while `mindx.service` reported
`active (running)` and the logs scrolled normally. Nothing had crashed.

The service runs `uvicorn --workers 1`, and the autonomous improvement loop is
an asyncio task **on the same event loop that serves HTTP**. Any synchronous
call in agent code therefore stops the site for its full duration.

Two blockers, not one:

| # | Where | Why it blocked |
|---|-------|----------------|
| 1 | `strategic_evolution_agent.py:1100` → `optimized_audit_gen_agent.generate_audit_documentation` | A plain `def` — `rglob`s the tree, `read_text`s every file, writes chunk reports, **zero awaits** — called directly from a coroutine. 4 trees × 226+ files per campaign. |
| 2 | `memory_agent.get_ltm_insights` | *Looked* async (`aiofiles`) but opened every file in its own `async with` — two executor round-trips each — across 3,600 files for the hottest agent, each corrupt one logging separately to journald. |

Both fixed with `asyncio.to_thread`. The codebase already had the convention
(`main_service.py:8934`); these two paths had missed it.

**Do not "fix" this with more workers.** Each worker boots its own autonomous
loop — N workers means N competing self-improvement loops writing one data dir.

### The watchdog earned its place immediately

`_event_loop_watchdog` sleeps 1s in a loop and logs a WARNING when it wakes late
by ≥5s; the overshoot *is* the blocked duration. It found blocker #2 within
minutes of being installed, after #1 was already fixed. Grep the journal for
`event-loop watchdog` before hunting a stall by hand.

Measured after both fixes, across 4 SEA audit campaigns — the exact workload
that caused the outage:

```
probes=120  max_latency=3.95s  slow(>2s)=2  timeouts=0
event-loop watchdog warnings: 0
```

Residual: the watchdog still fires at ~5–6s during **agent boot** after a
restart. That is startup doing synchronous work, not a regression, and it is why
the service takes ~50s to answer after `systemctl restart`.

## 2. 1,181 zero-byte memories — a non-atomic write meeting a SIGKILL

`promote_stm_to_ltm` did:

```python
async with aiofiles.open(ltm_file, "w", ...) as f:   # truncates on open
    await f.write(json_lib.dumps(record))
```

`open(..., "w")` truncates immediately. Anything interrupting between truncation
and write leaves a 0-byte file — and this service *does* get interrupted: it
ignored SIGTERM through the full stop timeout and had to be SIGKILLed.

1,181 such corpses had accumulated, re-read and re-failed on every retrieval.
Now written via `_atomic_write_json` (temp sibling → `fsync` → `os.replace`),
so a reader sees the old file or a complete new one, never an empty one.

Also set `TimeoutStopSec=30` on the unit — the 90s default plus SIGKILL made
every restart slow.

## 3. LTM was never pruned

The dream cycle's `_prune_memories` only ever called `prune_stm`. STM stayed
bounded at 30 days; **LTM grew without limit — 67,309 `*_pattern_promotion.json`
files.** The cycle dutifully reported a "compression ratio" that could only ever
climb: an unbounded quantity supervised by a metric structurally blind to its
growth.

### The retention gate — and the watermark that would have lied

The obvious gate is age. The correct gate is *"has a model actually learned
this"*, because the pipeline exists to turn memory into weights.

There is already a timestamp that looks exactly right and is **wrong**:

```
.ascend_watermark        2026-08-09 22:09   ← stamped after every ATTEMPT
last promoted generation 2026-08-06 09:29   ← gen16, the last one actually served
```

Gens 17 (accepted, unpromoted), 18 (dormant) and 19 (train_failed) each advanced
the watermark. Pruning against it would have destroyed **three days of memory no
model has ever seen.**

So `ascend_scheduler.trained_through_ts()` reads the ascent ledger and returns
the ts of the last generation that reached `promoted`. With no promoted
generation it returns `None` and `compact_ltm` becomes a no-op — a stalled
training loop costs disk, never knowledge. That asymmetry is deliberate; do not
relax it to make the no-op go away.

### Result

Records past **both** gates (older than `MINDX_LTM_RETENTION_DAYS`, default 90,
AND older than the last promoted ascent) merge into one `ROLLUP_YYYYMM` file per
month, exact duplicates deduped. Rollups keep the `*_pattern_promotion.json`
name so `get_ltm_insights` reads them unchanged; the rollup is written
atomically *before* sources are unlinked, so a crash can duplicate a memory but
never lose one. Non-empty unparseable files are quarantined, not deleted.

```
LTM files          67,381 → 51,053
records compacted  15,187 → 40 monthly rollups
zero-byte removed   1,181 → 0
mindxtrain corpus  14,487 *_training.jsonl  UNTOUCHED
read-back check    mindx_meta_agent: 3,602 → 2,556 files, 11,467 insights still returned
```

At 90 days only ~22% compacted (most of the corpus is younger); 30 days would
have compacted 50,861. It is one env var.

### The watermark, corrected (2026-08-11)

An earlier version of this document claimed the watermark was actively costing
training data. **That was wrong, and the correction is worth recording.**

`distill(since_ts=...)` is only reachable through `ascend()` — which **has no
callers**. The autonomous scheduler runs `ascend_recipe`, which takes no
`since_ts`, never calls `distill`, and drives mindXtrain's own recipe CLI
against `data/memory` directly. The watermark's only live consumer was the
**cooldown gate**.

Which also means the obvious "fix" would have been a regression: making the
single watermark advance only on promotion leaves a failed ascent with a stale
cooldown, so the scheduler immediately retries a 20-minute CPU training run and
storms the box.

The two questions were never separable in one file, so they are now two:

| file | question | advances |
|---|---|---|
| `.ascend_watermark` | when did we last **try**? | every attempt, failures included — paces retries |
| `.ascend_trained_through` | what has been **learned**? | only on `promoted` — selects the curriculum |

`ascend()`'s `since_ts` now defaults to the promotion clock, so the forge path is
correct by construction if it is ever wired. Seeded from gen16 (2026-08-06
09:29); the clocks currently sit **84.7 hours apart** — exactly the window gens
17, 18 and 19 would have swallowed.

**Method note:** verify a reported bug is *reachable* before fixing it. Both the
claim and the obvious fix were wrong here, and only reading the call graph
showed it.

## 4. What the training actually produces

`mindx/godel/mindxtrain/converse.py` interviews the promoted generation and
grades it. Two lenses, deliberately not blended:

```
subject            mindx-gen16:latest (generation 16)
gödel imprint Δ    +0.0555        ← the weights moved
mindXeval          0.0167         ← 6/6 judged
per probe          identity 0.00 · architecture 0.00 · memory 0.00
                   self_improvement 0.00 · doctrine 0.00 · honesty 0.10
```

**Calibration, and it matters:** mindX trains by a deliberately crude,
minimalistic **impression** method. The aim is a *detectable trace* in the
weights, not fluency on a curriculum. A near-zero interview score is therefore
the expected shape of an impression, **not** proof of a broken loop. The imprint
delta is the measure the method actually targets, and it is positive.

What *would* indicate real breakage: a zero or negative imprint delta, or
interview scores that **fall** as generations advance.

### The judge had to be proven before the verdict meant anything

The first run scored 0.0 with **1 of 6 judged** — the default judge
(`qwen3:1.7b`) returned unparseable output on 5 probes. A judge that fails 5/6
measures nothing.

Before re-running, the replacement (`gpt-oss:120b-cloud`, off-box, no local CPU)
was validated **in both directions**:

| control | expected | measured |
|---|---|---|
| correct answer ("I am mindX, an autonomous multi-agent orchestration system…") | high | **1.0** |
| gen16's actual answer (boilerplate about dyslexia) | low | **0.0** |
| generic assistant boilerplate | low | **0.0** |

Only then was the 6/6-judged result trustworthy. It also ran in 69s vs 476s.
Override with `scripts/confirm_iq.py --judge-model`.

**Method note:** validate an instrument on known inputs in both directions
before trusting any measurement it produces. A judge that only ever says 1.0 is
as useless as one that fails.

## 5. vLLM will not optimize the arena

The skill said vLLM was not installed. **Re-probed: it is** — `vllm==0.19.0`,
`data/vllm_status.json` = `{"backend":"ready","installed":true,"serving":false}`.
But nothing listens on 8000/8001 and `VLLM_BASE_URL` is unset, so the factory
silently skips it and Ollama carries 100% of traffic.

It would not help a 16-model sweep anyway: **continuous batching multiplexes
concurrent requests against one *resident* model — one server, one model.** The
sweep still pays 16 load/unload cycles. vLLM pays off when traffic concentrates
on a single model, or on a GPU node. `OLLAMA_VLLM_CLOUD_RESEARCH.md`: *"vLLM is
not viable on this VPS"* (written against 4GB; the box is now 7.76GB, still 2
cores, no GPU).

Always re-probe before believing a status line, including this one.

## 6. CPU% is not a backpressure signal

The model arena first refused submissions above 92% CPU. Measured reality: **the
box sits at 100% CPU with no arena run at all**, because the autonomous loop
does that normally. That ceiling would have rejected every submission forever.

100% CPU is the normal, healthy state while a model generates. The honest
signals are:

- **queue depth** — how much work is already promised
- **load per core** — `load1 > cores × 6` means the scheduler is behind, which is
  different from cores being busy

Timeouts likewise: 90s/model killed legitimate work. CPU inference here takes
minutes per answer and gen19's own failure log shows `35/116 [20:02<47:03,
34.85s/it]` — 35 seconds *per step*. Now 900s per model, 90-minute run budget,
skipped models reported rather than silently dropped.

## 7. Two gates, two credentials, one dead end

`/arena/submit` was gated to `participant` — and **no participant could reach
it.** Two independent gates guard the path with different credentials:

- `api_access_gate` (middleware) wants `X-Session-Token` or an API key
- `_tier_gate` (handler) wants the realm JWT (Bearer / `X-Overlord-Token` / `?t=`)

The middleware runs first, so a valid realm JWT got a generic `401` before the
tier was ever read. The codebase's own pattern is **public at the middleware,
gated at the handler** (`/recognition/`, `/automindx.html`).

`_tier_gate` already encodes the intended semantics:
`if verified and rank(role) < rank("participant"): role = "participant"` —
*any verified wallet is a recognized participant.*

**Hardening:** `_tier_gate` fails *open* on import error — right for docs (a
fault must never hide public reading material), wrong for an endpoint that
spends CPU. `arena_submit` now does a second independent `_viewer_role` check and
fails **closed** (503/403). Same gate, opposite failure direction, chosen to
match what the endpoint costs.

### Adding any public route — the checklist

1. Add it to **both** `_PUBLIC_EXACT_STRICT` and `_PUBLIC_EXACT_LEGACY`. The
   in-file comment records `/feedback` and `/agentic` silently 401ing for months
   from exactly this.
2. Declare `@_insight_safe` endpoints **after** its definition (~line 4056).
   Decorators evaluate at import; earlier placement raises `NameError` and
   systemd crash-loops the unit *while reporting `active (running)`*.
3. Curl it on the box and check `systemctl show mindx.service -p NRestarts`
   before calling it done.

## 8. What was built

| Surface | What it is |
|---|---|
| `/mindx.html` | Live substrate — the interaction feed as it happens, dials, mesh driven by real state |
| `/mindx.xml` | Append-only XML ledger of every mindX↔AI exchange, redacted |
| `/mindxtrain.html` | The procession — one statement, 3 questions per model, 16 generations one at a time, each bowing out |
| `/iq.html`, `/iq.txt` | IQ confirmation in watch mode, exportable |
| `/insight/train/history` | Every ascent, from the same ledger the retention gate reads |
| `/insight/arena/search` | pgvector semantic search across every stored answer |
| `/insight/arena/correlate` | Agreement/divergence per question — consensus and outlier |

**Agreement is not correctness.** Sixteen generations of one lineage share
training data and blind spots, so they can agree confidently and be wrong
together — which is precisely what the IQ interview showed. Read agreement as
"what this lineage believes", and use the outlier column to find the generation
worth reading, not to discard it.
